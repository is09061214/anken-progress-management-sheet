スプレッドシートの下に並ぶタブ（シート）は6つ。全部を見る必要はなく、自分の役割に合った1〜2枚だけを見れば回るように作られています。

ダッシュボード

BOが毎朝見る

信号ごとの件数、「いま確認が必要な案件」（赤・黄）、「情報不足の案件」（灰）の3ブロック。マスターの信号列を集計しているだけなので、常に最新です。

マスター

全員が触る本体

1行＝1本の動画。タイトル入力・担当アサイン・ステータス更新はここ。締切と信号は数式が自動で埋めるので、グレーの列は触りません。

担当者ビュー

編集者向け

名前をプルダウンで選ぶと、自分が制作担当・サムネ担当の案件だけが締切の近い順に並びます。編集者に共有する用の「自分専用の窓」です。

設定

ルールの置き場

締切日数（順算設定）、メンバー名簿、案件タイプ表、ステータス定義表。ここの数字や行を変えるだけでシート全体の挙動が変わり、プログラムの修正は不要です。

自動追加設定

ロボットの設定

クライアントごとの「1撮影あたり何本」「投稿曜日」「カレンダー上の別名」、Discord通知の送り先URL、名前とDiscordアカウントの対応表を置きます。

自動追加ログ

ロボットの日誌

毎朝の自動処理が「何を追加し、何をスキップし、何を通知したか」を1行ずつ記録。同じ撮影予定を二重に追加しないための記憶装置でもあります。

ここがポイント：「頭脳」と「顔」の分離

判定（赤・黄・青・灰）はすべてスプレッドシートの数式で行い、WebダッシュボードやDiscord通知はその結果を写して見せるだけです。だから「赤の基準を7日から5日にしたい」と思ったら、シートの数式を直せば全部に反映され、アプリの再デプロイ（プログラムの入れ替え）は不要です。 出典: リポジトリ README「判定ルールを変えたいときはスプレッドシートを編集すればよく、アプリの再デプロイは不要」

ちょっと補足：なぜ「チェックボックス」ではなく「プルダウン」なのか

ひとつ前の世代（本番シート・新）は工程ごとにチェック✓を6個並べ、その組み合わせからステータスを自動判定していました。しかし進行役2人から「信号が青ばかりで優先順位が分からない」「誰がボールを持っているか分からない」という声が出て、V2で旧シートで慣れていた11ステータスを人が直接選ぶ方式に戻しました。その代わり「締切を過ぎてもステータスが進んでいない＝更新忘れ」を信号（黄）で検知する仕組みを付けています。 出典: sheet/v2-kaizen/index.html「きっかけ」「最大の変更」

締切の自動計算 ── 撮影日から「順算」する

案件タイプで工程を省略

「撮影なし」「制作のみ」「サムネなし」を選ぶと、該当しない工程の締切は空欄になり、判定からも外れます（設定シートL〜Q列の○／—表）。

撮影日が空のとき

設定J6で切替。「逆算で仮計算」なら投稿予定日から引き算で仮締切を出す（既定）。「情報不足(灰)」なら締切を出さず灰信号にする厳格モード。

なぜ「逆算」から「順算」に変えたのか

前の世代は投稿予定日から引き算する「逆算」でした（制作10日前・サムネ8日前・CL提出5日前）。しかし実際の現場では撮影が終わらないと制作が始められないため、投稿日が遠くても撮影が遅れれば締切は後ろにずれます。そこで「撮影日から順に足す＋公開リミットを見張る」方式に切り替え、ずれが「破綻」として見えるようにしました。 出典: sheet/v2-kaizen/index.html「締切を逆算から順算＋リミット監視へ」、sheet/案件進捗管理シート_生成スクリプト.gs のリードタイム表

赤＝要対応

条件はひとつだけ、投稿予定日まで7日以内。工程がどこにあっても赤になります。「7日あればゼロから編集しても間に合う」最後のラインという意味です。

やること：担当者に直接連絡して進捗を確認する。

黄＝もうすぐ（更新忘れ検知）

今のステータスに対応する締切を過ぎたのに、ステータスが進んでいない。本当に遅れているか、シートの更新をサボっているかのどちらかです。破綻した案件もここ。

やること：今日中に目を通してステータスを直す。黄を消す＝シートを最新に保つこと。

青＝順調・完了

見なくていい案件。完了行はさらにグレーになり、マスターのフィルタで隠れます（フィルタを開けば再表示可能）。

やること：なし。

灰＝情報不足

タイトル・投稿予定日・ステータス・制作担当・BO担当のどれかが空欄。判定材料がないので信号を出せない状態です。ダッシュボードに「何が足りないか」が列挙されます。

やること：空欄を埋める。埋めた瞬間に他の色へ変わる。

ちょっと補足：ルールは3回変わっている

初代は「赤＝公開3日以内または締切超過／黄＝公開7日以内」、次に「赤＝2日以内／黄＝5日以内」、そして2026-08-09から現在の「赤＝7日以内だけ／黄＝締切超過または破綻」になりました。「赤は日付だけ、黄は更新忘れ」と役割を分けたのが今のルールの肝です。古い解説ページには前のルールが残っていることがあります。

失敗は赤い帯で明示

シートを読めなかったときは前回のデータを表示しつつ、画面上部に赤いバナーでエラーを出す。こっそりサンプル表示に化けることはない。

健康診断URL

「/healthz」にアクセスすると鮮度と最終エラーを返す。更新間隔の3倍（3時間）以上古ければ異常（503）扱い。

Web版の更新も自動

Web版のプログラムは GitHub（プログラムの保管庫）で管理されていて、main ブランチに変更を入れると GitHub Actions が自動で Cloud Run（Googleのサーバー貸しサービス）へ配置し直します。対象は dashboard フォルダ内の変更だけ。図解ページや Apps Script を直しても再配置は走りません。 出典: .github/workflows/cloud_run_deploy.yml、dashboard/README.md

毎朝の自動化 ── 誰も起きていない時間に4体のロボットが働く

ここからが「通知と自動機能」の本題です。スプレッドシートには Apps Script（アップススクリプト＝Googleのスプレッドシートに組み込める小さなプログラム）が4本仕込まれていて、毎朝5時台から7時台にかけて順番に起動します。イメージは、開店前のお店で掃除係・仕入れ係・催促係・点検係が順に回ってくる感じです。

毎朝のタイムライン（日本時間・土日祝も動く）

5時台 数式の修理係 safeRebuildSignalFormulas

マスターの信号ドット・現在担当・現在締切・信号の4列（B/T/U/V）を点検。数式が消えた、#REF!（参照切れエラー）になった、行がずれたセルだけを正しい数式に張り替える。壊れたセルが0なら何も書かない。

6時台 案件の受付係 safeAutoAddFromCalendar

Googleカレンダーの「【撮影】〇〇」予定を探し、クライアントごとの本数ぶんマスターに行を追加。結果を Discord に報告。

続けて「締切の催促係」も動く（sendProgressReminders_）。制作締切が明日以前なのに未着手・タイトル待ちの案件を、担当者を名指しして Discord へ。

6:15〜6:45 朝礼の号令係 kickMorningNotify

GitHub に「朝の進捗通知を今すぐ流して」と合図を送る。GitHub 側が画像付きのサマリを作り、Discord に全員宛で投稿。月曜だけは「撮影予定リマインド」も追加で流す。

7時台 壊れ点検係 safeDailyRefErrorScan

マスターの全セルを見て #REF! が残っていないか点検。見つけたときだけ、セル番地と直し方を Discord に通知する（修理はしない）。

終日 Webダッシュボード

60分ごとにシートを読み直し、最新の信号を表示し続ける。

時刻は Apps Script の「時間主導トリガー」の性質上、その1時間内のどこかで起動します。出典: sheet/エラー通知Discord切替.gs の setupErrorNotifyTriggers、sheet/GitHub朝通知キック.gs

基本ルール：「朝の進捗通知」以外は、来ない朝＝ぜんぶ順調

進捗サマリだけは毎朝必ず届きますが、自動追加・催促・点検・エラーの通知は「何か報告すべきことがあった日だけ」届きます。通知が静かな朝は、ロボットが動いていないのではなく、報告することがなかったという意味です。

通知カタログ ── Discord に届く7種類のメッセージ

通知はすべて Discord（チームのチャットツール）に届きます。送り方は「Webhook（ウェブフック）」という「このURLに文章を送ると、そのチャンネルに投稿される」専用の投函口。チャンネルごとに投函口が分かれているので、通知の種類で届く場所が変わります。まずは一番よく見るものから。

ロボットが毎朝6時台にやっている6ステップ

1
カレンダーを見に行く

今日の7日前〜90日先までの予定を取得し、タイトルに「【撮影】」を含むものだけを拾う。「（仮）」で始まる予定は見送り（確定したら「（仮）」を消せば翌朝拾われる）。

2
クライアント名を照合する

「【撮影】」の後ろから「@」の前までを名前として取り出し、「自動追加設定」の名前と別名（例: DEP／ディーイーピー）に先頭一致・長い名前優先で当てはめる。見つからなければ「一覧に無い名前」として通知し、追加はしない。

3
本数ぶんの行を作る

設定表の「本数/撮影」だけ行を追加（例: DEP_m は8本、多くのクライアントは3〜4本、四国物産_m は1本、未設定なら標準4本）。仮タイトルは「7/23撮影 ①」「7/23撮影 ②」…、撮影日はその日付、ステータスは「タイトル待ち」、BO担当は設定表の既定値。

4
投稿予定日を割り振る

設定表に投稿曜日（例: 水・日）があれば、そのクライアントの最後の投稿予定日の続きから曜日を順に埋める。前の投稿がない、または撮影日＋14日より前なら「撮影日＋14日以降の最初の該当曜日」から。曜日が未設定なら空欄のまま（通知に「投稿日は手動入力待ち」と出る）。

5
日誌に書いて、二重追加を防ぐ

「自動追加ログ」に予定のID・状態（追加済／スキップ等）を記録。翌朝以降は同じIDが「追加済」なら触らない。だから同じ予定が毎日増え続けることはない。

6
追加済みの予定に変化がないか見張る

過去に追加した予定をもう一度カレンダーで確認し、消えていれば「予定削除」、日付が変わっていれば「撮影日変更 7/26 → 7/29」を通知し、該当行のメモ欄にも追記。行そのものは書き換えないので、人がシートを直す。

守り係 ── 「壊れない」「止まらない」ための裏方

自動化は「動かすこと」より「止まらないこと」が難しい。このシートには、数式の破損・Googleの一時的な混雑・GitHubの遅延という3つの敵に対する備えが入っています。

敵1：数式の破損

行の削除や並べ替えで、数式の参照先が消えると「#REF!」というエラーになり、その行の信号が消えます。

5時台・自動修理：信号系4列だけは、壊れたセルを正しい数式で上書き。50セル超なら列ごと張り替え。
7時台・全体点検：他の列も含めて #REF! を探し、あればセル番地と直し方を通知（修理はしない）。
敵2：Googleの一時的な混雑

早朝は「Service Spreadsheets timed out（時間切れ）」のような一時エラーが出ることがあります。

3回まで再挑戦：失敗したら45秒待ってやり直す。開始から4分を超えたら打ち切り（Apps Scriptの6分制限対策）。
結果をDiscordへ：2回目以降で成功なら「復旧しました」、全滅なら「エラーが起きました」。Googleの失敗メールに埋もれない。
GitHub側も：シート読み取りが混雑エラー（429/5xx）なら30秒待って最大3回。
敵3：GitHubの時計の遅れ

朝の通知はもともと GitHub の「毎日6:30に実行」という予約機能で動いていましたが、2026年8月末から2〜8時間遅れる日が続出しました。

9/1から方式変更：Apps Script の時計（正確）が6:30ごろ GitHub に「今すぐ実行」の合図を送る。合図での実行は待ち行列に並ばず数秒で始まる。
合鍵：合図には GitHub のトークン（期限付きの合鍵）が必要。期限切れは「testGithubToken」で確認できる。

「自動追加設定」H〜I列

Discord Webhook URL（2本）、スキャン範囲（過去7日・未来90日）、初回投稿リードタイム（14日）、新規行のステータス、超過通知の上限（30日）、BOロールのID。赤の「7日」だけはマスターの数式側。

工程の組み合わせを変えたい

「設定」シート 案件タイプ表（L〜Q列）

タイプごとに「撮影／制作／サムネ／CL提出／公開設定」を○か—で指定。—の工程は締切が空欄になり、判定から外れる。

用語集

BO
このチームで案件の進行を回す担当（増田さん・岩渕さん）。ステータス更新、クライアント共有、公開設定・納品を担う。
CL
クライアント。「CL提出」＝クライアントに動画を見せること。
順算・逆算
順算＝起点（撮影日）に日数を足して締切を出す。逆算＝ゴール（投稿日）から日数を引いて出す。現行は順算。
破綻
順算したCL提出締切が公開リミットを追い越した状態。物理的に間に合わないスケジュール。
Apps Script
Googleのスプレッドシートに組み込める小さなプログラム。ここでは毎朝の自動処理4本を担当。
時間主導トリガー
「毎日○時台に実行」という Apps Script の目覚まし時計。正確な分は指定できず、その1時間内のどこかで動く。
Webhook（ウェブフック）
Discord が発行する専用URL。ここに文章や画像を送ると、決まったチャンネルに投稿される投函口。
GitHub Actions
GitHub（プログラムの保管庫）が用意する、合図や時刻で自動的にプログラムを走らせてくれる借りパソコン。
Cloud Run
Googleのサーバー貸しサービス。Webダッシュボードはここで24時間動いている。
サービスアカウント
人ではなくプログラム専用のGoogleアカウント。シートに「閲覧者」として招待され、通知やダッシュボードがこれで読む。
#REF!
数式の参照先が消えたときに出るエラー。行削除・並べ替えが主な原因。
フィルタ表示
自分にだけ見える絞り込み。他の人の画面に影響しないので、共同編集中はこれを使う。
